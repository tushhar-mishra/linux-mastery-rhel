# 049 · LVM: Physical Volumes, Volume Groups and Logical Volumes

> **You need first:** [048 · Mounting and fstab](048-mounting-and-fstab.md)
> **Next:** [050 · Swap](050-swap.md)

---

## What it is

**LVM** (Logical Volume Manager) is a flexible layer between disks and filesystems. Instead of putting a filesystem straight onto a partition, you:

1. Turn disks or partitions into **PVs** (Physical Volumes).
2. Pool them into a **VG** (Volume Group): one big bucket of storage.
3. Cut **LVs** (Logical Volumes) out of the bucket. Each LV behaves like a disk partition: you put a filesystem on it and mount it.

| Term | Meaning |
|---|---|
| **PV** | A disk or partition prepared for LVM (it gets an LVM label and metadata area) |
| **VG** | A pool made from one or more PVs |
| **PE** (Physical Extent) | The pool's allocation unit: **4 MiB by default**. Everything is counted in whole extents |
| **LV** | A virtual block device carved from a VG |
| **LE** (Logical Extent) | One extent of an LV, mapped to one PE somewhere in the VG |

RHEL installs `/` and swap on LVM by default (you saw `rhel-root` and `rhel-swap` in `lsblk`). Ubuntu Server's installer also offers LVM.

```
/dev/vdb1   /dev/vdc        ← partitions or whole disks
   PV          PV           ← pvcreate
   └─────┬─────┘
     VG "vgdata"            ← vgcreate (a pool of 4 MiB extents)
   ┌─────┴─────┐
 LV "lvweb"  LV "lvdb"      ← lvcreate
 XFS /web    ext4 /db       ← mkfs + mount + fstab
```

## Why it exists

With plain partitions, growing a filesystem usually means downtime: unmount, back up, repartition, restore. With LVM you can:
- **grow** a volume **online** in one command when it fills up;
- **add disks** to the pool at any time;
- make a volume **span** several disks;
- **move** data off a failing disk while it's in use (`pvmove`, topic 086);
- take **snapshots** for backups or safe upgrades (topic 052);
- add thin provisioning, striping, RAID, caching and encryption layers (Part 11).

## Analogy

PVs are **buckets of water** (disks). The VG is a **big tank** you pour them into. LVs are **bottles you fill from the tank**, labelled `web` and `db`. Need a bigger `web` bottle? Pour more from the tank, without emptying the bottle. Tank running low? Pour in another bucket (add a PV). The extents are the **measuring cups**: you always fill in whole cups.

## How it works inside

- `pvcreate` writes an **LVM label** and a **metadata area** near the start of the device.
- The VG's **metadata** (a small text description: which PVs, which LVs, which extents each LV uses) is stored on **every PV** in the VG, so the VG can be rebuilt as long as enough PVs survive. Copies are also saved automatically under `/etc/lvm/backup/` and `/etc/lvm/archive/` (topic 052).
- Each LV becomes a **device-mapper** device. Device mapper is a kernel framework that builds virtual block devices out of real ones using a mapping table ("LV block 0–262143 → PV `vdb1` blocks 2048–264191…"). You see it as `/dev/dm-0`, with friendly symlinks `/dev/VG/LV` and `/dev/mapper/VG-LV`. (In mapper names, a hyphen inside a VG or LV name is doubled: `my-vg` → `my--vg`.)
- Growing an LV just appends more extents to its mapping table, which is **instant** and works while mounted. Then the **filesystem** must be told to use the new space (`xfs_growfs` / `resize2fs`). `lvextend -r` does both.
- LV sizes are always whole extents; requests get rounded up ("Rounding up size to full physical extent").
- **RHEL 9/10 "devices file":** LVM only uses devices listed in `/etc/lvm/devices/system.devices`. A disk carrying a VG from another machine is **ignored** until you import it (`vgimportdevices`). This prevents LVM grabbing the wrong disks.

## Commands

| | PV | VG | LV |
|---|---|---|---|
| Create | `pvcreate` | `vgcreate` | `lvcreate` |
| Short list | `pvs` | `vgs` | `lvs` |
| Details | `pvdisplay` | `vgdisplay` | `lvdisplay` |
| Grow | `pvresize` | `vgextend` | `lvextend` |
| Shrink | `pvresize` | `vgreduce` | `lvreduce` |
| Remove | `pvremove` | `vgremove` | `lvremove` |

### Build it

```bash
lsblk                                         # identify the empty disk FIRST
sudo parted -s /dev/vdb mklabel gpt mkpart lvm1 1MiB 100% set 1 lvm on
sudo pvcreate /dev/vdb1
sudo pvcreate /dev/vdc                         # a whole disk works too (no partition)
```
```
  Physical volume "/dev/vdb1" successfully created.
  Creating devices file /etc/lvm/devices/system.devices
  Physical volume "/dev/vdc" successfully created.
```
- The first `pvcreate` creates `/etc/lvm/devices/system.devices`, the list of disks LVM is allowed to use on RHEL 9/10 (topic 086 explains why). Every PV you create is added to it automatically.
- `pvcreate: command not found`? Install `lvm2`. It's always present when the system itself is on LVM, but some cloud and Vagrant images leave it out.
```bash
sudo vgcreate vgdata /dev/vdb1 /dev/vdc
sudo vgcreate -s 16M vgbig /dev/vdd1           # custom extent size (a power of 2)
```

```bash
sudo lvcreate -n lvweb -L 1G vgdata            # by size (K, M, G, T)
sudo lvcreate -n lvdb  -l 100 vgdata           # by number of extents: 100 × 4 MiB = 400 MiB
sudo lvcreate -n lvlogs -l 50%FREE vgdata      # a share of the free space (or 100%FREE, 20%VG)
```
```
  Logical volume "lvweb" created.
```

### Look at it

```bash
sudo pvs ; sudo vgs ; sudo lvs
```
```
  PV         VG     Fmt  Attr PSize  PFree
  /dev/vdb1  vgdata lvm2 a--  <5.00g  <3.61g
  /dev/vdc   vgdata lvm2 a--  <5.00g 712.00m
  VG     #PV #LV #SN Attr    VSize VFree
  vgdata   2   3   0 wz--n-- 9.99g 4.30g
  LV     VG     Attr       LSize   Pool Origin Data%  Meta%  Move Log Cpy%Sync Convert
  lvdb   vgdata -wi-a----- 400.00m
  lvlogs vgdata -wi-a-----   4.30g
  lvweb  vgdata -wi-a-----   1.00g
```
- `PFree`/`VFree` = unallocated space left. `#PV #LV #SN` = how many PVs, LVs and snapshots.
- LV `Attr` `-wi-a-----`: `w` writeable, `i` "inherit" allocation policy, `a` **active** (usable). A missing `a` means the LV isn't activated.

```bash
sudo lvs -o +devices
```
```
  LV     VG     Attr       LSize   … Devices
  lvdb   vgdata -wi-a----- 400.00m   /dev/vdb1(256)
  lvlogs vgdata -wi-a-----   4.30g   /dev/vdc(0)
  lvweb  vgdata -wi-a-----   1.00g   /dev/vdb1(0)
```
- Which PVs each LV sits on, and from which extent number. `lvlogs` (4.30 GiB) fitted on `vdc` alone, so LVM put it there in one piece. An LV spreads across several PVs only when no single PV has enough free space (or when you ask for striping, topic 085). `(256)` means "starting at extent 256 of that PV"; the first 256 extents of `vdb1` belong to `lvweb`.

```bash
sudo vgdisplay vgdata | grep -E 'PE Size|Total PE|Free  PE'
ls -l /dev/vgdata/ /dev/mapper/ | head
```

### Filesystem and permanent mount

```bash
sudo mkfs.xfs /dev/vgdata/lvweb
sudo mkdir -p /web
echo "UUID=$(sudo blkid -s UUID -o value /dev/vgdata/lvweb) /web xfs defaults 0 0" | sudo tee -a /etc/fstab
sudo systemctl daemon-reload && sudo mount -a && findmnt /web
```
- `blkid -s UUID -o value` prints just the UUID. `/dev/mapper/vgdata-lvweb` is also stable and fine in fstab.

### Grow online (the everyday task)

```bash
sudo vgs                                           # is there enough VFree?
sudo lvextend -r -L +500M /dev/vgdata/lvweb        # grow LV AND filesystem (-r = resize fs)
df -hT /web
```
```
  File system xfs found on vgdata/lvweb mounted at /web.
  Size of logical volume vgdata/lvweb changed from 1.00 GiB (256 extents) to <1.49 GiB (381 extents).
  Extending file system xfs to <1.49 GiB (1598029824 bytes) on vgdata/lvweb...
xfs_growfs /dev/vgdata/lvweb
meta-data=/dev/mapper/vgdata-lvweb isize=512    agcount=4, agsize=65536 blks
...
data blocks changed from 262144 to 390144
xfs_growfs done
  Extended file system xfs on vgdata/lvweb.
  Logical volume vgdata/lvweb successfully resized.
Filesystem               Type  Size  Used Avail Use% Mounted on
/dev/mapper/vgdata-lvweb xfs   1.5G   61M  1.4G   5% /web
```
- LVM finds the filesystem, grows the LV, then runs `xfs_growfs` for you (you can see the command it ran). Everything happens while `/web` stays mounted.

| Form | Meaning |
|---|---|
| `-L +500M` | Grow **by** 500 MiB |
| `-L 2G` | Grow **to** 2 GiB |
| `-l +100%FREE` | Use all the free space in the VG |

Without `-r`, grow the filesystem yourself: XFS → `sudo xfs_growfs /web` (**mount point**, must be mounted); ext4 → `sudo resize2fs /dev/vgdata/lvdb` (device).

**Not enough free space in the VG?** Add a disk to it first:
```bash
sudo pvcreate /dev/vdd ; sudo vgextend vgdata /dev/vdd
```

**The virtual disk itself got bigger** (a cloud volume or VM disk resized)? Grow the partition (`growpart /dev/vdb 1`, from the cloud-utils-growpart package), then `sudo pvresize /dev/vdb1`, then `lvextend -r`.

### Shrink (ext4 only, unmounted)

XFS **cannot** shrink. For ext4, the **filesystem must shrink before the LV**, or you destroy data:
```bash
sudo umount /db
sudo lvreduce -r -L 300M /dev/vgdata/lvdb      # -r: checks and shrinks the fs first, then the LV
sudo mount -a
```
```
  File system ext4 found on vgdata/lvdb.
  File system size (400.00 MiB) is larger than the requested size (300.00 MiB).
  File system reduce is required using resize2fs.
  File system fsck will be run before reduce.
  Reducing file system ext4 to 300.00 MiB (314572800 bytes) on vgdata/lvdb...
e2fsck /dev/vgdata/lvdb
...
resize2fs /dev/vgdata/lvdb 307200k
...
  Reduced file system ext4 on vgdata/lvdb.
  Size of logical volume vgdata/lvdb changed from 400.00 MiB (100 extents) to 300.00 MiB (75 extents).
  Logical volume vgdata/lvdb successfully resized.
```
- Try the same on the XFS volume and LVM refuses before touching anything: `File system reduce is required and not supported (xfs).`

### Remove (in this order)

```bash
sudo umount /web
sudo vi /etc/fstab                        # delete its line FIRST, or the next boot fails (topic 048)
sudo lvremove /dev/vgdata/lvweb           # ⚠️ data gone
sudo vgremove vgdata
sudo pvremove /dev/vdb1 /dev/vdc
```

### Try it
1. Build `vgdata` from two disks, with three LVs (1G XFS, 400 MiB ext4, the rest unused). Mount them in fstab by UUID.
2. Fill one with `dd if=/dev/zero of=/web/fill bs=1M count=900`, see it nearly full in `df`, then `lvextend -r -L +500M` while it's still mounted.
3. Create a VG with `-s 16M` and an LV with `-l 20`. What size do you get?
4. Shrink the ext4 LV with `lvreduce -r`, then tear everything down in the right order.

## Where you'll use it

- **"Disk full" on `/var` or a database volume** → `lvextend -r` online: the most common LVM task in production.
- **Cloud VMs:** grow the volume in the console, then `growpart` + `pvresize` + `lvextend -r`, with no downtime.
- **Swapping a failing or old disk** with `pvmove` while services run (topic 086).
- **Snapshots** before risky upgrades (topic 052).
- **Kubernetes:** local-storage drivers like TopoLVM and OpenEBS LVM create one LV per persistent volume claim.

## When it breaks

| Symptom | Cause | Fix |
|---|---|---|
| `Insufficient free extents` | The VG is out of space | `vgextend` with a new PV, or ask for less |
| The LV is bigger but `df` isn't | The filesystem wasn't grown | `xfs_growfs MNT` / `resize2fs DEV`; next time use `-r` |
| `Can't open /dev/vdb1 exclusively. Mounted filesystem?` | Wrong device, or it's in use | `lsblk -f`; pick the right one |
| `Cannot use /dev/vdb: device is partitioned` | The whole disk has a partition table | Use the partition, or `wipefs -a` an unused disk |
| A VG from another machine doesn't show up | It's not in the devices file | `sudo vgimportdevices VG` or `lvmdevices --adddev /dev/X` |
| `Logical volume … contains a filesystem in use` | It's mounted | Unmount first |
| An LV shows no `a` in Attr; `/dev/VG/LV` missing | Not activated | `sudo vgchange -ay VG` |
| Data lost after a shrink | The LV was reduced before the filesystem | Restore from backup. Always use `lvreduce -r` |
| Boot fails after `lvremove` | fstab still points at it | Fix fstab (topic 057) |

## Quick recap

- Disks → `pvcreate` → `vgcreate` (pool of 4 MiB extents) → `lvcreate -L size | -l extents | -l 100%FREE` → mkfs → mount.
- `/dev/VG/LV` = `/dev/mapper/VG-LV` = a device-mapper device. Check with `pvs`, `vgs`, `lvs -o +devices`.
- Grow online with **`lvextend -r`**; add space with `vgextend` or `pvresize`. XFS never shrinks; ext4 shrinks offline with `lvreduce -r`.
- Remove in order: umount → fstab → lvremove → vgremove → pvremove.

**Interview questions**

1. *Explain PV, VG and LV.* A PV is a disk or partition initialised for LVM; a VG pools one or more PVs into extents; an LV is a virtual block device carved from the VG, which you format and mount.
2. *How do you grow a filesystem on LVM without downtime?* If the VG has free space, `lvextend -r -L +SIZE /dev/VG/LV`; otherwise add a PV with `vgextend` (or `pvresize` after growing the disk) first.
3. *What's a physical extent and why does it matter?* The allocation unit of a VG (default 4 MiB). LV sizes are always multiples of it, and `-l` sizes are counted in extents.
