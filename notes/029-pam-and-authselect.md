# 029 · PAM and authselect: How Logins Are Checked

> **You need first:** [028 · sudo and su](028-sudo-and-su.md)

## What it is

**PAM** (Pluggable Authentication Modules) is the shared framework that login-related programs (`login`, `sshd`, `su`, `sudo`, `passwd`, Cockpit, …) use to answer: *Is this really you? Are you allowed in right now? What should happen when your session starts?*

Instead of each program having its own password code, they all call PAM, and PAM runs a configurable **stack of modules**: small plug-ins such as "check the local password", "check password strength", "lock after 3 failures", "apply resource limits".

**authselect** is the RHEL tool that **generates** the shared PAM files (and the matching NSS settings) from tested profiles, so you don't hand-edit them. Ubuntu/Debian don't use authselect; there the equivalent is `pam-auth-update`, and the shared files are `/etc/pam.d/common-auth`, `common-account`, `common-password` and `common-session`.

## Why it exists

Security policies change: "lock accounts after 5 failures", "passwords need 12 characters", "allow logins from directory users", "only the ops group may SSH in". With PAM you change **configuration**, not the programs. One change applies to SSH, the console, sudo and su alike.

## Analogy

PAM is the **security checkpoint at an airport**. Every gate (ssh, login, sudo) sends passengers through the same checkpoint. The checkpoint has a **line of stations** (modules): passport check, banned-list check, bag size limits. The airport can add, remove or reorder stations without rebuilding the gates. authselect is **head office handing out approved checkpoint layouts**, so local staff don't improvise a broken one.

## How it works inside

### The four module types

| Type | Question it answers | Examples |
|---|---|---|
| `auth` | Who are you? Prove it | Password check (`pam_unix`), directory login (`pam_sss`), lockout (`pam_faillock`) |
| `account` | Are you allowed in **now**? | Expired? Locked? Allowed at this time? From this host? |
| `password` | Rules for **changing** a password | Strength (`pam_pwquality`), history (`pam_pwhistory`) |
| `session` | Set-up and clean-up around the session | Resource limits (`pam_limits`), umask (`pam_umask`), create the home directory (`pam_mkhomedir`) |

### Rule format and control flags

```
<type>     <control>    <module>              [arguments]
auth       required     pam_faillock.so       preauth
auth       sufficient   pam_unix.so           try_first_pass
account    required     pam_unix.so
password   requisite    pam_pwquality.so      local_users_only
session    optional     pam_umask.so
auth       include      system-auth
```

| Control | Behaviour |
|---|---|
| `required` | Must succeed. On failure, PAM keeps running the rest (so an attacker can't tell which step failed), then fails |
| `requisite` | Must succeed. On failure, **stop immediately** |
| `sufficient` | If it succeeds (and nothing `required` failed before it), **stop with success** for this type. Its failure is ignored |
| `optional` | Only matters if it's the only module of its type |
| `include` / `substack` | Pull in another file's rules |
| `[success=1 default=ignore]` | Advanced bracket syntax with full control |

### The flow for one SSH password login

1. sshd calls PAM with service name `sshd`, so PAM reads `/etc/pam.d/sshd`.
2. That file `include`s the shared stacks (`password-auth`, `postlogin`) that authselect generated.
3. **auth**: `pam_faillock` checks for too many recent failures → `pam_unix` checks the password against `/etc/shadow` (or `pam_sss` asks the directory).
4. **account**: `pam_unix` checks aging and expiry (topic 023); other modules check times, lists or access rules.
5. **session**: limits are applied, the umask is set, the home directory is created if missing, and the login is recorded.

**SSH key logins skip the `auth` stage**, but `account` and `session` still run. So any rule that must apply to key logins too (time windows, allow-lists) belongs in **`account`**.

### Files

| Path | Contents |
|---|---|
| `/etc/pam.d/<service>` | The stack for one program (`sshd`, `login`, `su`, `sudo`, `passwd`, `cockpit`) |
| `/etc/pam.d/system-auth`, `password-auth`, `postlogin`, … | Shared stacks. On RHEL these are **symlinks into `/etc/authselect/`** and are regenerated by authselect |
| `/etc/security/*.conf` | Module settings: `pwquality.conf`, `faillock.conf`, `limits.conf`, `time.conf`, `access.conf`, `pwhistory.conf` (each with a `.d/` folder for drop-ins) |

PAM files are read **on every login**, so changes apply immediately, with no restart. That also means **a mistake can lock everyone out immediately.**

**Safety rules for PAM changes:** keep a root session **open** while you test, back up `/etc/pam.d`, test with a **new** login in another window, use a test user, and take a VM snapshot.

## Commands

### authselect

```bash
authselect current
```
```
Profile ID: local
Enabled features:
- with-silent-lastlog
- with-mdns4
```
- The active profile (`local` = local accounts only; `sssd` = directory users through SSSD, topic 030) and its features.

```bash
authselect list
authselect list-features local
sudo authselect enable-feature with-faillock     # ADD one feature to the current profile
sudo authselect disable-feature with-faillock
sudo authselect select sssd with-mkhomedir --force   # REPLACES the profile + feature set ⚠️
authselect backup-list
```
Common features: `with-faillock` (lockout), `with-mkhomedir` (create home at first login), `with-pwhistory` (block reuse), `without-nullok` (no empty passwords), `with-fingerprint`, `with-smartcard`.

### Inspect a stack

```bash
cat /etc/pam.d/sshd
```
```
#%PAM-1.0
auth       substack     password-auth
auth       include      postlogin
account    required     pam_sepermit.so
account    required     pam_nologin.so
account    include      password-auth
password   include      password-auth
session    required     pam_selinux.so close
session    required     pam_loginuid.so
session    required     pam_selinux.so open env_params
session    required     pam_namespace.so
session    optional     pam_keyinit.so force revoke
session    optional     pam_motd.so
session    include      password-auth
session    include      postlogin
```
- `pam_nologin` blocks non-root logins while the file `/etc/nologin` exists (handy during maintenance). `pam_loginuid` records your original login identity for auditing (topic 077). `pam_selinux` sets your SELinux context (topic 072).

### Password strength (`pam_pwquality`)

```bash
sudo tee /etc/security/pwquality.conf.d/90-local.conf <<'EOF'
minlen = 12
dcredit = -1
ucredit = -1
lcredit = -1
ocredit = -1
enforce_for_root
EOF
```
- A **negative** credit means "at least this many of that kind": `dcredit=-1` = at least 1 digit (`u` = uppercase, `l` = lowercase, `o` = other/symbol).
- Other options: `minclass`, `maxrepeat`, `dictcheck`, `usercheck`.
- Root only gets a warning unless `enforce_for_root` is set.

### Account lockout (`pam_faillock`)

```bash
sudo authselect enable-feature with-faillock
sudo tee -a /etc/security/faillock.conf <<'EOF'
deny = 3
unlock_time = 600
fail_interval = 900
EOF
```
- After 3 failures within 15 minutes, the account is locked for 10 minutes. root isn't locked unless `even_deny_root` is set.

```bash
sudo faillock --user testalice
```
```
testalice:
When                Type  Source                                           Valid
2026-11-16 13:20:01 RHOST 192.168.56.1                                         V
2026-11-16 13:20:07 RHOST 192.168.56.1                                         V
2026-11-16 13:20:12 RHOST 192.168.56.1                                         V
```
```bash
sudo faillock --user testalice --reset
```
- Each failure, with its source address. `--reset` unlocks the account.

### Resource limits (`pam_limits`)

A **limit** (ulimit) caps what one user's processes can use, for example `nofile` (how many files can be open at once) or `nproc` (how many processes).

```bash
sudo tee /etc/security/limits.d/90-app.conf <<'EOF'
appuser  soft  nofile  65536
appuser  hard  nofile  65536
appuser  hard  nproc   4096
EOF
su - appuser -c 'ulimit -n; ulimit -u'
```
```
65536
4096
```
- **soft** = the current limit (the user can raise it up to hard); **hard** = the ceiling.
- **systemd services ignore `limits.conf`**, because they don't log in through PAM. Set `LimitNOFILE=` in the unit file instead (topic 098). This catches out many people tuning databases.

### Allow-list for SSH (`pam_listfile`)

```bash
echo alice | sudo tee /etc/ssh/allowedusers ; sudo chmod 600 /etc/ssh/allowedusers
# add to the ACCOUNT section of /etc/pam.d/sshd (so it also covers key logins):
#   account required pam_listfile.so item=user sense=allow file=/etc/ssh/allowedusers onerr=fail
```
For SSH, `AllowUsers`/`AllowGroups` in `sshd_config` (topic 066) is usually simpler.

### Time windows (`pam_time`) and restricting `su`

```bash
# /etc/pam.d/sshd (account):   account required pam_time.so
# /etc/security/time.conf:     sshd;*;contractor;Wk0900-1700     (weekdays 09:00-17:00 only)

# /etc/pam.d/su — uncomment this line so only wheel members may use su:
auth  required  pam_wheel.so use_uid
```

### Common modules

| Module | Purpose |
|---|---|
| `pam_unix` | Local `/etc/passwd`/`/etc/shadow` |
| `pam_sss` | Directory users via SSSD |
| `pam_pwquality` / `pam_pwhistory` | Strength / no reuse |
| `pam_faillock` | Lockout after failures |
| `pam_limits` | Resource limits |
| `pam_time` / `pam_access` | Time-based / origin-based access |
| `pam_wheel` | Restrict `su` to wheel |
| `pam_nologin` | Block logins while `/etc/nologin` exists |
| `pam_env`, `pam_umask`, `pam_mkhomedir` | Environment, umask, create home |

### Try it
(Use a VM snapshot and keep a root session open.)
1. Run `authselect current` and read `/etc/pam.d/sshd`.
2. Set `minlen = 12` and test `passwd` as a test user.
3. Enable faillock with `deny = 3`, fail 3 logins, check `faillock --user`, then reset.
4. Set a `nofile` limit for a test user and check `ulimit -n` after `su -`.

## Where you'll use it

- **Security baselines** (CIS, STIG = Security Technical Implementation Guide) require lockout, password quality and history, all done through PAM.
- **Joining a domain** (Active Directory / FreeIPA): `authselect select sssd with-mkhomedir` (topic 030).
- **"Too many open files"** for a user-run app: `limits.d`. For a systemd service: `LimitNOFILE` (topic 098).
- **Maintenance windows:** `touch /etc/nologin` blocks non-root logins.
- **Brute-force monitoring:** `faillock` and `/var/log/secure`.

## When it breaks

| Symptom | Cause | Fix |
|---|---|---|
| Nobody can log in after a PAM edit | A syntax or logic error in a stack | Restore the backup from your still-open root session; otherwise rescue boot (topic 057) |
| Your manual edits to `system-auth` vanished | authselect regenerated the file | Use authselect features or a custom profile |
| Lockout never triggers | The faillock feature isn't enabled | `authselect enable-feature with-faillock` |
| A restriction is bypassed with SSH keys | The rule is in the `auth` stack | Move it to `account` |
| `authselect: … files were modified outside` | Hand edits detected | Review; `authselect select … --force` or restore |
| Limits don't apply to a service | systemd doesn't use pam_limits | `LimitNOFILE=` etc. in the unit |
| Users can't log in, "System is going down" or similar | `/etc/nologin` exists | Remove it |

## Quick recap

- PAM = a stack of modules per service in `/etc/pam.d/`. Types: **auth, account, password, session**. Controls: required, requisite, sufficient, optional, include.
- On RHEL, the shared stacks are generated by **authselect** (`current`, `enable-feature with-faillock`). Ubuntu uses `pam-auth-update` and the `common-*` files.
- Settings live in `/etc/security/*.conf(.d)`: pwquality, faillock, limits, time, access.
- SSH keys skip `auth`, so put access rules in `account`. systemd services ignore `limits.conf`.

**Interview questions**

1. *What are the four PAM module types?* auth (prove identity), account (allowed now?), password (changing credentials), session (set-up and clean-up).
2. *`required` vs `requisite`?* Both must succeed. `requisite` stops at once on failure; `required` runs the rest of the stack first, then fails.
3. *Does PAM's auth stack run for SSH key logins?* No. sshd verifies the key itself, but the account and session stacks still run, so access rules for key logins belong in account.
