## What it is

**Name resolution** turns a name like `db1.example.com` into an IP address (and sometimes the reverse).

- **DNS** (Domain Name System): the worldwide, distributed "phone book" of names.
- **`/etc/hosts`**: a local, hand-written name → IP list on each machine.
- **`/etc/nsswitch.conf`** (topic 030): decides the **order** sources are checked in (`hosts: files dns myhostname`).
- **`/etc/resolv.conf`**: which **DNS servers** (resolvers) to ask, plus search domains and options.
- **Resolver** (recursive DNS server): the server that does the full lookup for you and caches answers (your company's DNS, `1.1.1.1`, `8.8.8.8`).
- **Authoritative server**: the server that holds the real records for a domain (topic 081 runs one).
- **FQDN** (Fully Qualified Domain Name): the complete name, like `web1.example.com.` (the final dot = the root).
- **TTL** (Time To Live): how many seconds an answer may be cached.
- **systemd-resolved**: a local caching resolver service, used by default on **Ubuntu**; RHEL doesn't use it by default.

## Why it exists

People and configs use **names**; the network needs **IPs**. Names let you move a service to a new IP without touching every client. DNS also carries other important data: mail servers (MX), service locations (SRV), verification (TXT). And "**it's always DNS**" is an industry joke for good reason: slow or wrong resolution causes timeouts, failed deployments and outages that look like anything but DNS.

## Analogy

Looking up a name is like **finding a phone number**:
1. First you check **your own contacts list** (`/etc/hosts`).
2. If it's not there, you call **directory enquiries** (your resolver).
3. Directory enquiries doesn't know every number. It asks the **international operator** (root servers) "who handles `.com`?", then the **`.com` operator** "who handles `example.com`?", then **example.com's own receptionist** (the authoritative server) "what's the number for `web1`?"
4. It tells you the answer and **remembers it for a while** (cache, TTL).

## How it works inside

### What happens when a program looks up `web1.example.com`

1. The program calls glibc's `getaddrinfo()`.
2. glibc reads **`/etc/nsswitch.conf`** → `hosts: files dns myhostname`:
   - `files` → check **`/etc/hosts`**. A match there wins, and DNS is never asked.
   - `dns` → ask the DNS servers listed in **`/etc/resolv.conf`**.
   - `myhostname` → always resolve the machine's own name and `localhost`.
3. For DNS, glibc sends a query over **UDP port 53** (TCP for big answers) to the first `nameserver`. If it doesn't answer within `timeout` seconds, it tries the next. There's a maximum of 3 nameservers.
4. The **resolver** checks its cache. If the answer isn't there, it does the **recursive** walk: root servers → `.com` servers → `example.com`'s authoritative servers → the answer. It caches the answer for its TTL.
5. If the name has **fewer dots** than `ndots` (default 1), glibc first tries it with each **`search`** domain appended (`web1` → `web1.example.com`).

**RHEL doesn't run a local DNS cache by default**, so every lookup goes to the configured servers. Programs may cache answers themselves (Java, browsers, nscd/systemd-resolved if enabled).

### /etc/resolv.conf

```
# Generated by NetworkManager
search example.com corp.example.com
nameserver 10.0.0.53
nameserver 10.0.0.54
options timeout:2 attempts:2
```
| Line | Meaning |
|---|---|
| `nameserver` | DNS servers to ask, in order (max 3) |
| `search` | Domains appended to short names |
| `options ndots:N` | A name with fewer than N dots gets the search domains tried **first** |
| `options timeout:N attempts:N` | Seconds per try / number of rounds |

**On RHEL, NetworkManager writes this file** from the profiles' `ipv4.dns` / `ipv4.dns-search` (topic 060). Hand edits are overwritten. **On Ubuntu**, it's usually a link to systemd-resolved's stub (`nameserver 127.0.0.53`); the real servers are shown by `resolvectl status`.

### Common record types

| Record | Purpose |
|---|---|
| `A` / `AAAA` | Name → IPv4 / IPv6 |
| `CNAME` | Alias → another name |
| `PTR` | IP → name (reverse lookup) |
| `MX` | Mail servers for a domain |
| `NS` | The authoritative servers for a domain |
| `SOA` | Zone information (serial, timers, negative-cache TTL) |
| `TXT` | Free text (SPF, domain verification) |
| `SRV` | Where a service runs (`_ldap._tcp.example.com`) |

## Commands

### Hostname and the hosts file

```bash
hostnamectl hostname                    # show (set with: sudo hostnamectl hostname NAME)
cat /etc/hosts
```
```
127.0.0.1   localhost localhost.localdomain localhost4 localhost4.localdomain4
::1         localhost localhost.localdomain localhost6 localhost6.localdomain6
192.168.56.11  server2.example.com server2
```
```bash
echo '192.168.56.11  server2.example.com server2' | sudo tee -a /etc/hosts
```
- Format: `IP  canonical-name  aliases…`.

### The right test: what programs actually see

```bash
getent hosts server2
getent ahosts www.redhat.com | head -2
```
```
192.168.56.11   server2.example.com server2
23.38.58.41     STREAM e3396.dscx.akamaiedge.net
23.38.58.41     DGRAM
```
- `getent` follows nsswitch exactly like applications do (files, then DNS).
- `ahosts` shows what a program would get from `getaddrinfo()`: one line per address and socket type (`STREAM` for TCP, `DGRAM` for UDP). The name on the first line is the **canonical** name, reached after following CNAME aliases (here `www.redhat.com` is an alias that ends at a CDN host). Use `getent hosts NAME` for a simple "IP name" answer.

### dig: ask DNS directly

```bash
sudo dnf install -y bind-utils         # dig, host, nslookup (Ubuntu: dnsutils)
dig www.example.com
```
```
; <<>> DiG 9.18.33 <<>> www.example.com
;; global options: +cmd
;; Got answer:
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 41721
;; flags: qr rd ra ad; QUERY: 1, ANSWER: 2, AUTHORITY: 0, ADDITIONAL: 1

;; OPT PSEUDOSECTION:
; EDNS: version: 0, flags:; udp: 1280
;; QUESTION SECTION:
;www.example.com.		IN	A

;; ANSWER SECTION:
www.example.com.	1	IN	A	104.20.23.154
www.example.com.	1	IN	A	172.66.147.243

;; Query time: 51 msec
;; SERVER: 10.0.2.3#53(10.0.2.3) (UDP)
;; WHEN: Tue Nov 17 00:31:33 UTC 2026
;; MSG SIZE  rcvd: 76
```

| Part | Meaning |
|---|---|
| `status: NOERROR` | Success. **`NXDOMAIN`** = the name doesn't exist. **`SERVFAIL`** = the resolver couldn't get an answer (broken upstream or DNSSEC). `REFUSED` = the server won't answer you |
| `flags: qr rd ra ad` | `rd` = you asked for recursion, `ra` = the server offers it, `ad` = the resolver validated the answer with DNSSEC. `aa` would mean an authoritative answer |
| `OPT PSEUDOSECTION` | EDNS: an extension that lets DNS messages be larger than 512 bytes (`udp: 1280` = the size offered). It is the "1" in `ADDITIONAL: 1` |
| `ANSWER SECTION` | Name, **TTL in seconds** (here only 1 s left in the cache), class `IN`, type `A`, the value. Two lines = two addresses; clients may use either |
| `Query time` | How long the lookup took. A slow resolver shows up here |
| `SERVER:` | Which DNS server answered |

```bash
dig +short www.example.com              # just the answer
dig +short -x 8.8.8.8                   # reverse lookup (PTR)
dig MX gmail.com +short                 # mail servers
dig @1.1.1.1 www.example.com            # ask a SPECIFIC server (compare with yours)
dig +trace www.example.com              # follow the whole chain from the root servers
host www.redhat.com                     # short and friendly
```

**`dig` ignores `/etc/hosts`.** If `getent` works but `dig` fails, the name exists only in `/etc/hosts`.

### Setting DNS servers (permanently)

```bash
sudo nmcli con mod lab ipv4.dns "10.0.0.53 10.0.0.54" ipv4.dns-search example.com
sudo nmcli con mod lab ipv4.ignore-auto-dns yes      # ignore DNS servers handed out by DHCP
sudo nmcli con up lab ; cat /etc/resolv.conf
```

### Ubuntu: systemd-resolved

```bash
resolvectl status          # the real upstream servers per interface
resolvectl query www.example.com
resolvectl flush-caches
```

### Try it
1. Add `server2` to server1's `/etc/hosts`. Compare `getent hosts server2` with `dig server2`.
2. `dig www.redhat.com` twice and watch the TTL count down (the resolver's cache).
3. `dig @1.1.1.1` vs `dig @8.8.8.8` for the same name: compare times.
4. Add a dead first nameserver (`10.255.255.1`) in front of a working one and time `getent hosts www.redhat.com` (each lookup waits for the timeout). Then remove it.

## Where you'll use it

- **"Can't connect to db.internal":** `getent hosts` first. Most "network" problems are name resolution.
- **Slow everything** (SSH logins, curl, package installs) = often a dead or slow first nameserver. Each lookup waits `timeout` seconds before trying the next.
- **Kubernetes:** pods get `nameserver <CoreDNS IP>`, `search <ns>.svc.cluster.local svc.cluster.local cluster.local` and **`options ndots:5`**. An external name like `api.github.com` (2 dots < 5) is first tried with each search suffix, which multiplies DNS queries; that's why people append a trailing dot or tune ndots. Service names like `my-svc.my-namespace` resolve thanks to the search list.
- **Migrations and failovers:** lower the TTL before changing a record's IP, so caches pick up the change quickly.
- **Service discovery:** SRV records (Active Directory, Kerberos), and internal DNS zones in clouds (Route 53 private zones).

## When it breaks

| Symptom | Cause | Fix |
|---|---|---|
| `getent` works, `dig` fails | The name is only in `/etc/hosts` | Expected; add it to DNS if needed |
| `dig` works, the application fails | `/etc/hosts` overrides it with a wrong IP, nsswitch order, or the app has cached it | Check `/etc/hosts`; `getent`; restart the app |
| Everything is slow to start or connect | The first `nameserver` is dead | Fix the order; `options timeout:1` |
| `NXDOMAIN` for an internal name | Missing search domain, or a typo | Use the FQDN; set `ipv4.dns-search` |
| `SERVFAIL` | The resolver can't reach the authoritative servers, or DNSSEC validation failed | `dig @other-resolver`; `dig +trace` |
| Your edit to `/etc/resolv.conf` disappeared | NetworkManager rewrote it | Set DNS with nmcli |
| An old IP is still returned after a change | Caching (TTL) | Wait out the TTL; flush the caches you control |
| Ubuntu: `nameserver 127.0.0.53` but nothing resolves | systemd-resolved is down or misconfigured | `resolvectl status`; `systemctl status systemd-resolved` |

## Quick recap

- Lookup order from `/etc/nsswitch.conf`: `files` (`/etc/hosts`) → `dns` (`/etc/resolv.conf` servers) → `myhostname`.
- Test what apps see with **`getent hosts NAME`**; query DNS directly with **`dig`** (`+short`, `@server`, `-x`, `+trace`). `dig` ignores `/etc/hosts`.
- `resolv.conf`: `nameserver` (max 3), `search`, `options ndots/timeout/attempts`. RHEL: NetworkManager writes it; Ubuntu: systemd-resolved (`resolvectl`).
- `NXDOMAIN` = doesn't exist; `SERVFAIL` = the resolver failed; TTL = cache lifetime.

**Interview questions**

1. *What happens when a program resolves a hostname on Linux?* glibc follows `/etc/nsswitch.conf`: checks `/etc/hosts`, then queries the DNS servers in `/etc/resolv.conf` (applying search domains and ndots). The resolver walks root → TLD → authoritative servers if it doesn't have the answer cached.
2. *`dig` vs `getent hosts`?* `dig` queries DNS servers directly and ignores `/etc/hosts`. `getent` uses the system's full resolution path (nsswitch), so it shows what applications actually get.
3. *Why do Kubernetes pods sometimes make many DNS queries for one external name?* `ndots:5` plus several search domains make the resolver try the name with each cluster suffix before trying it as an absolute name.
