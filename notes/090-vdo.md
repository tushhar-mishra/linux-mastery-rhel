## What it is

**VDO** (Virtual Data Optimizer) is a block layer that makes data take **less physical space**, inline (as it is written), using three tricks:

1. **Zero-block elimination**: blocks that are all zeros are not stored at all.
2. **Deduplication**: identical 4 KiB blocks are stored **once**; later copies just point at the first.
3. **Compression**: remaining blocks are compressed (LZ4) and packed together.

On RHEL 9 and 10, VDO is an **LVM volume type** (`lvcreate --type vdo`); the old standalone `vdo` manager command is gone. On RHEL 10 the kernel target is `dm-vdo` (upstream since kernel 6.9). The `vdo` package still provides `vdostats`.

| Term | Meaning |
|---|---|
| **VDO pool LV** | A hidden LV holding the real, deduplicated and compressed data. Its size (`-L`) is the **physical** size |
| **VDO LV** | The volume you format and mount. Its size (`-V`) is the **virtual** size, usually larger than the pool |
| **Dedupe index** (UDS) | An in-memory + on-disk index of block fingerprints (hashes), used to find duplicates |

Ubuntu/Debian: `dm-vdo` is in recent upstream kernels, but distribution tooling is limited; VDO is mostly a RHEL feature.

## Why it exists

Many workloads store the **same data over and over**: dozens of VMs cloned from one template, nightly backups that are 95% unchanged, container images sharing base layers, log files full of repeated text. VDO can store 3–10× more on the same disks for that kind of data.

## Analogy

A **library that keeps only one copy of each book**. When someone donates a book the library already has, the librarian just adds a card saying "another copy lives at shelf 12" (deduplication). Blank notebooks aren't shelved at all (zero elimination), and long books are shelved as compact paperbacks (compression). The catalogue (the index) is how the librarian spots duplicates quickly.

## How it works inside

1. Each 4 KiB write to the VDO LV is checked: all zeros? → just record "zero" in the block map.
2. Otherwise VDO computes a **hash** (fingerprint) and looks it up in the **dedupe index**. If an identical block already exists (verified by comparing data), VDO only increments a reference count and maps the new logical block to the existing physical block.
3. New, unique blocks are **compressed**, and several compressed blocks are packed into one physical block.
4. A **block map** translates virtual (logical) block numbers to physical locations, just like a thin pool (topic 085).
5. Because the virtual size is bigger than the physical pool, it behaves like **thin provisioning**: **the physical pool can fill up while `df` still shows free space**. Monitor the pool, not `df`.
6. Deleted files only free physical space after **discards** (`fstrim`).
7. The cost: **CPU** for hashing and compression, and **RAM** for the index (roughly 0.5–1 GB+ depending on index size), plus a minimum pool size of a few GB for metadata.

**Order of layers matters.** Encrypted or already-compressed data looks random and never deduplicates, so VDO must receive **plaintext**. With encryption (LUKS, topic 088), stack it like this, from the disk up:

```
disk  →  LUKS (dm-crypt)  →  VDO  →  filesystem
```
The filesystem writes plaintext into VDO, VDO deduplicates and compresses it, and LUKS encrypts the result before it reaches the disk. The wrong order (disk → VDO → LUKS → filesystem) makes VDO see only ciphertext, and it saves nothing.

## Commands

```bash
sudo dnf install -y lvm2 vdo
sudo pvcreate /dev/vdb ; sudo vgcreate vg_vdo /dev/vdb
sudo lvcreate --type vdo -n lv_vdo -L 10G -V 30G vg_vdo/vpool0
```
```
    The VDO volume can address 6 GB in 3 data slabs, each 2 GB.
    It can grow to address at most 16 TB of physical storage in 8192 slabs.
    If a larger maximum size might be needed, use bigger slabs.
  Logical volume "lv_vdo" created.
```
- 10 GiB of real disk (`-L`) presented as a 30 GiB volume (`-V`). Part of the physical space goes to VDO's own metadata and index, so usable physical space is smaller than 10 GiB.

```bash
sudo mkfs.xfs -K /dev/vg_vdo/lv_vdo        # -K: don't discard the whole virtual size at mkfs (much faster)
sudo mkdir -p /vdo
echo "UUID=$(sudo blkid -s UUID -o value /dev/vg_vdo/lv_vdo) /vdo xfs defaults 0 0" | sudo tee -a /etc/fstab
sudo systemctl daemon-reload && sudo mount -a
```

### See the savings

```bash
sudo dd if=/dev/urandom of=/vdo/random.bin bs=1M count=500   # random: no savings
sudo cp /vdo/random.bin /vdo/copy.bin                        # duplicate: almost free
sudo dd if=/dev/zero of=/vdo/zeros.bin bs=1M count=500       # zeros: free
sync ; sudo vdostats --human-readable
df -h /vdo
```
```
Device                    Size      Used Available Use% Space saving%
vg_vdo-vpool0-vpool      10.0G      4.6G      5.4G  46%           66%
Filesystem                    Size  Used Avail Use% Mounted on
/dev/mapper/vg_vdo-lv_vdo      30G  1.7G   29G   6% /vdo
```
- `df` says 1.7 GB used of 30 GB (the **virtual** view). `vdostats` shows the **physical** truth: 4.6 GB used on the pool (much of it VDO's own metadata), and 66% space saving: 1.5 GB of files stored in roughly 0.5 GB of new data.

```bash
sudo lvs -a -o lv_name,lv_size,data_percent,vdo_compression,vdo_deduplication vg_vdo
```
```
  LV             LSize  Data%  VDOCompression VDODeduplication
  lv_vdo         30.00g
  vpool0         10.00g 46.12  enabled        enabled
  [vpool0_vdata] 10.00g
```

### Tune and grow

```bash
sudo lvchange --compression n vg_vdo/lv_vdo        # turn compression off (y to turn on)
sudo lvchange --deduplication n vg_vdo/lv_vdo
sudo fstrim -v /vdo                                # return deleted blocks to the pool
sudo systemctl enable --now fstrim.timer
sudo lvextend -L +5G vg_vdo/vpool0                 # grow the PHYSICAL pool (needs free VG space)
sudo lvextend -L +20G vg_vdo/lv_vdo ; sudo xfs_growfs /vdo   # grow the VIRTUAL size + filesystem
```

**Sizing guidance (Red Hat):** virtual ≈ **10×** physical for VM or container images, ≈ **3×** for object storage. Measure real savings for your data before committing.

### Try it
1. Create a 10 GiB-physical / 30 GiB-virtual VDO LV with XFS.
2. Copy the same 500 MB file five times and watch `vdostats` barely move.
3. Write 500 MB of `/dev/urandom` and see that random data doesn't save anything.
4. Delete everything, check `vdostats`, run `fstrim`, check again.

## Where you'll use it

- **Virtualisation hosts** storing many similar VM images.
- **Backup targets** where nightly copies are mostly identical.
- **Container image storage** and build caches.
- **Not useful for:** databases with random data, media files (already compressed), or encrypted data.
- In the wider world, the same idea lives in ZFS dedup/compression, Btrfs compression, and storage arrays' built-in data reduction.

## When it breaks

| Symptom | Cause | Fix |
|---|---|---|
| Writes fail while `df` shows free space | The physical pool is full | `lvextend` the pool; `fstrim`; monitor `vdostats` |
| Little or no savings | Data is random, compressed or encrypted | Expected; VDO isn't a fit for that data |
| `mkfs` takes ages | It discards the whole virtual size | `mkfs.xfs -K` |
| `vdostats: command not found` | The package is missing | `dnf install vdo` |
| `lvcreate` refuses a small pool | Below VDO's minimum size | A bigger `-L` |
| High CPU / memory on the host | Hashing, compression, index | Expected cost; size the host accordingly, or disable compression |

## Quick recap

- VDO = inline zero-elimination + deduplication + compression, as an LVM type: `lvcreate --type vdo -n LV -L PHYSICAL -V VIRTUAL VG/POOL`.
- Format with `mkfs.xfs -K`; check real usage with **`vdostats --human-readable`**, not `df`.
- Behaves like thin provisioning: the physical pool can fill; use `fstrim` and monitoring.
- Great for VMs, backups and images; useless for random, compressed or encrypted data.

**Interview questions**

1. *What does VDO do?* It reduces physical storage with inline zero-block elimination, block-level deduplication and compression, presenting a larger virtual volume on a smaller physical pool.
2. *Why can writes fail on a VDO volume while `df` shows free space?* `df` shows the virtual size; the physical pool underneath is full. Monitor `vdostats` and grow the pool.
3. *Why does VDO save nothing on encrypted data?* Encryption makes every block look random and unique, so there are no duplicates and nothing compresses. Dedup must see the plaintext.
